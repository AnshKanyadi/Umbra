# ADR 0003: The file tree is Kleppmann's move operation

- Status: accepted
- Date: 2026-09-01
- Depends on: [ADR 0002](0002-crdt.md), [docs/threat-model.md](../threat-model.md)

## Context

A vault is a folder of markdown files in directories. Two devices can rename,
move, create and delete concurrently while offline, and must merge without
asking anyone — the relay cannot order anything, by construction
(threat model §2).

Text and structure are separate problems. ADR 0002 handles the contents of a
file. This is the shape of the folder.

## The hard case

**Concurrent moves that would create a cycle.** Device A moves directory `a`
into `b`. Device B, at the same moment, moves `b` into `a`. Neither is wrong on
its own; together they are impossible, because the result would make each the
other's ancestor and neither reachable from the root.

Naive designs get this wrong in three recognisable ways:

- **Apply both and repair afterwards.** The two devices repair differently and
  stay different.
- **Reparent one of them to the root.** Convergent only if both pick the same
  one, which requires the very ordering the design was avoiding, and it moves a
  directory somewhere the user never asked for.
- **Apply both and let the cycle exist.** Both directories and everything under
  them disappear from the vault, on both devices, permanently. The data is still
  in the log and gone from the user's folder, which is the worst of the three.

## Decision

**Kleppmann's move operation**, from *A highly-available move operation for
replicated trees* (Kleppmann, Gomes, Mulligan, Beresford). The tree is a set of
`(child, parent, name)` triples and there is exactly one operation: a move.

```
create   move a brand new id under a parent
rename   move a node under the SAME parent with a different name
move     move a node under a different parent
delete   move a node under the reserved TRASH node
```

Collapsing all four into one is not code golf. A design with a separate delete
has to answer what a delete concurrent with a move *into* the deleted directory
means, and every answer is a special case. Here there is no special case: both
are moves, they are ordered by timestamp, the later one wins, and
`Tree.MoveConcurrentWithDeleteOfTheDestination` asserts both replicas agree.

### Applying an operation is undo, do, redo

```
UNDO every logged operation with a LATER timestamp, in reverse order
DO   the new operation
REDO the undone operations, in timestamp order
```

(`src/crdt/tree.cc:225-252`.) The state becomes a function of the *set* of
operations ordered by timestamp and nothing else, so two replicas holding the
same set agree however they received it. Each log entry records what it
displaced, which is what makes the undo exact rather than approximate.

`Tree.ArrivalOrderDoesNotMatter` asserts this over all 24 permutations of a
four-operation set.

### What happens on a concurrent move that would create a cycle

**The operation is ignored. Not applied and repaired, not redirected to the
root — ignored, as though it had never been issued** (`src/crdt/tree.cc:171`).

The cycle check is part of `do`: if the move would make a node its own
ancestor, `do` records the operation and changes nothing. Because both replicas
process the same set in the same timestamp order, both ignore the *same* one —
the later timestamp — and the tree keeps both directories, one nested inside the
other, chosen by the earlier move.

`Tree.ConcurrentMoveIntoEachOtherIsResolvedByIgnoringOne` asserts that the two
replicas agree, that exactly one move survived, and that **neither directory
became unreachable**, which is the failure the third naive design produces.

**An ignored operation stays in the log**, and that is load-bearing rather than
tidy. The cycle check runs again on every redo, against whatever the tree is at
that point, so an operation illegal in one ordering may be legal once an older
operation arrives and changes the shape. `Tree.AnIgnoredMoveCanApplyLaterUnderADifferentOrder`
delivers a three-operation set in the worst possible order and reaches the same
tree as the replica that issued it.

### No causal delivery required

A tree operation is **never not-ready**. `TreeDoc::Apply` has no `kNotReady`
outcome, unlike the text CRDT: a move naming a parent that has not arrived yet
simply leaves the node detached from the root until it does, and undo/redo
sorts out the rest. That is a strictly stronger property than ADR 0002's text
operations have, and it comes for free from the replay.

## What was rejected

**A tree built from the text CRDT's primitives** — paths as strings, renames as
edits to a path field. Rejected because a directory move would be one operation
per descendant, so moving a folder of a thousand notes would be a thousand
operations, and a concurrent move of an ancestor would interleave with them.

**Last-writer-wins on a parent pointer, with no cycle handling.** This is what
several sync tools do. It is the third naive design above: it converges, and it
converges on a tree with a cycle, which presents to the user as files vanishing.
Rejected on that.

**A total order imposed by the relay.** Would make all of this trivial and is
forbidden: the relay is assumed hostile and cannot be trusted to order anything
(threat model §2). It is also the assumption that would have to be unwound
first if sharing were ever added.

**Operational transformation on tree operations.** Same objection as ADR 0002,
plus tree OT has a considerably worse correctness record than text OT.

## Identity comes from the OS rename signal, not from stat data

Phase 0 measured that Linux hands a freshly deleted file's inode number **and
its nanosecond mtime** to the next file created — 198 times out of 200 on
overlayfs. Nothing in `stat(2)` separates a rename from a delete-and-create on
that platform.

So the watcher's `kMoved`, which is derived from `IN_MOVED_FROM`/`IN_MOVED_TO`
and FSEvents' `ItemRenamed` (`src/watcher/hint.h:47`), is the signal that
produces a tree move. A `kCreated` produces a **new** object id, a `kMoved`
produces a move of the **existing** one, and the difference between them is a
notification bit rather than an inference from timestamps.

**A move remains zero text operations**, as ADR 0002 established: it changes one
triple in the tree and touches no document.

## Storage

Tree operations go in the same Basalt oplog under the same key layout —
`object || replica || counter` — filed under a reserved object id
(`TreeObject()`, `src/crdt/tree.cc:96`). They encode to the same opaque
`OpPayload` text operations do, so the oplog and the encryption layer handle
both identically and neither has to know which it is holding.

**A filename lives inside that payload**, as a single path component. Encrypting
the payload is therefore what keeps names off the relay, which is the
requirement from threat model §3.

## What this costs

Applying an operation older than ones already seen undoes and redoes everything
newer, so an operation arriving *k* positions out of order costs O(k). In
ordinary use *k* is zero. A replica rejoining after a long absence pays once,
proportional to what it missed.

## Log compaction

*Added 2026-09-02. ADR 0003 originally recorded this as owed work.*

The log is what makes undo possible, so it cannot simply be truncated at an
arbitrary point: an operation older than the truncation point would need to undo
entries that are gone.

### The condition

> A tree log may drop every entry whose timestamp counter is at or below `w`
> when all five of these hold.
>
> **1. The set of devices is known and enumerable.** Umbra is single-user with
> enrolled devices (threat model §1), so this is checkable. An open
> collaborative system could not state it, which is why this condition is
> available here and not in general.
>
> **2. Every enrolled device reports, authenticated, two things:** a per-source
> contiguous prefix mark `have[S]` — the highest counter from source `S` for
> which it holds *every* operation at or below it — and its own Lamport clock.
> The prefix property requires that sync delivers each source's operations in
> counter order, which the oplog key layout already gives (ADR 0001, and the
> big-endian counter in `MakeOpLogKey`).
>
> **3. `w` is a minimum over everything:**
>
> ```
> produced[S] = have_S[S]            # the source's own mark
> acked[S]    = min over devices D of have_D[S]
> w           = min( min over sources S with produced[S] > 0 of acked[S],
>                    min over devices D of clock_D )
> ```
>
> **A source that has produced nothing imposes no constraint**, and the
> qualifier is load-bearing rather than tidy. A device reporting no mark for
> source `S` means one of two things it cannot tell apart locally: `S` has
> produced nothing, or this device is missing everything from `S`. Only `S`
> distinguishes them, and it does — a device trivially holds all of its own
> operations, so `have_S[S]` says how far `S` has got. Without this qualifier a
> single device that has never touched the tree collapses the watermark for
> every device forever, which the first implementation did: the harness reported
> zero entries dropped over 420 schedules.
>
> Skipping a silent source is safe because the clock term still binds it —
> anything it produces later has a counter above `w`.
>
> **4. Entries with counter ≤ `w` are dropped.** A counter, deliberately, not a
> full OpId: comparing counters alone sidesteps the replica tiebreak, and an
> operation with a counter above `w` sorts above every dropped entry whatever
> its replica id.
>
> **5. After dropping through `w`, every arriving operation with counter ≤ `w`
> is treated as already seen** — exactly the rule ADR 0002 needed for text
> tombstones, and for the same reason: dropping the log entry does not drop the
> operation, and a peer or a relay may hand it back.

### Why it is sound

Three things could break undo, and each is closed by a different clause.

**An operation at or below `w` could still be in flight.** Closed by the first
term of clause 3: `acked[S]` is the point below which *every* device already
holds all of `S`'s operations, so nothing at or below it is undelivered.

**A device could still produce an operation at or below `w`.** This is the part
ADR 0002's text condition does not need, and getting it wrong is how a
plausible-looking condition becomes unsound. Delivery is not enough: a device
whose clock is at 2 while `w` is 5 will issue counter 3 next, which sorts below
`w` and would need to undo entries that are gone. Closed by the second term of
clause 3 — `w` never exceeds the slowest clock, and a Lamport clock only
advances, so every future operation from every device has a counter strictly
greater than `w`.

**An operation at or below `w` could be re-delivered.** Closed by clause 5.

### Why a hostile relay cannot exploit it

This is the clause that makes the condition usable against the adversary the
threat model actually assumes. `w` is a **minimum over authenticated reports**,
so the two things a relay can do are:

- **Withhold a report.** The device's marks are then unknown, treated as zero,
  and `w` collapses. Compaction becomes more conservative. Safe.
- **Replay an old report.** Marks only ever increase, so an old report is
  smaller and again lowers `w`. Safe.

What a relay must not be able to do is *inflate* a report, which would induce a
device to compact past the point where an old operation can still arrive. That
is why the reports are authenticated under the epoch key rather than merely
transmitted: a relay holds no key and cannot forge one.

**A device that lies about its own marks breaks this**, and that is out of
scope by construction — the threat model assumes a hostile relay, not a hostile
device, because a single user's device that is lying has already been
compromised and holds the plaintext anyway.

### What it costs, stated

**An enrolled device that never reports blocks compaction for the whole vault.**
A phone left in a drawer holds every device's tree log open. That is the same
cost ADR 0002's text condition carries and it has the same mitigation: removing
a device from the vault removes it from the acknowledgement set, and revocation
already exists for other reasons (threat model §6).

The log is small — an id, two object ids and a name per operation — so the cost
of *not* compacting is slow rather than sudden. That is an argument for the
condition being conservative, not an argument against having one.

## How this is held to account

`sim/` runs the tree through the same seeded, reproducible schedules the text
CRDT gets, with a reference model that computes the expected tree independently,
and with adversarial schedules for the cases above. Deliberate defects were
introduced one at a time to confirm the harness goes red. The tables are in the
phase report.
