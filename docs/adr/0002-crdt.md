# ADR 0002: The sequence CRDT is Fugue

- Status: accepted
- Date: 2026-09-01
- Depends on: [ADR 0001](0001-storage.md), [docs/threat-model.md](../threat-model.md)

## Context

Umbra syncs folders of markdown files between one user's devices, with no
server able to read them and no server able to order anything. Two devices can
edit the same note while both are offline and must merge without asking anyone.
That is a sequence CRDT for text.

The requirement that decides the design is not convergence. Every sequence CRDT
converges — that is the definition. The requirement is that the converged
answer is one a person would accept.

## The anomaly that decides it

Two people, or one person on two devices, type at the same place while
disconnected. Device A types `Hello`, device B types `World`. On merge, the
result must be `HelloWorld` or `WorldHello`. It must not be `HWeolrllod`.

That failure is **interleaving**, and it is not hypothetical: it is what several
widely deployed designs do, in a case that is easy to reach.

**RGA interleaves, and here is exactly when.** In RGA each character records the
character it comes *after*. Type left to right and each character anchors to the
previous one, forming a chain — two concurrent chains sort against each other
once, at their heads, and come out whole. But **type backward** — put the cursor
somewhere and press left after each character, or paste repeatedly at one
position — and every character anchors to *the same* preceding character. They
are all siblings of one node, and a concurrent backward run's characters sort in
among them by timestamp. The result alternates character by character.

This is not an argument from a paper. It is reproducible in this repository:
replacing the insert rule in `src/crdt/text_doc.cc` with RGA's — always attach
as a right child of the left origin — and running the convergence harness
produces, on the first seed:

```
<>adbcadbcadbcadbcadbcadbc
```

Four replicas, each typing one character at a time at one anchor, perfectly
shuffled. See the phase report's deliberate-breakage table, defect B5.

## Decision

**Fugue**, as described by Weidner and Kleppmann. Each character is a node in a
tree that records *which node it was inserted next to* and **which side of it**.
The document is the in-order traversal.

The whole design is two lines. To insert between adjacent nodes `l` and `r`:

```
if l has no right children:  the new node is a RIGHT child of l
else:                        the new node is a LEFT  child of r
```

Why that removes the anomaly:

- **Typing forward makes a right-chain.** Insert `a` between `l` and `r`; `a`
  has no right children, so `b` becomes `a`'s right child, then `c` becomes
  `b`'s.
- **Typing backward makes a left-chain.** Insert `c` between `l` and `r`; if `l`
  already has right children, `c` becomes `r`'s *left* child. Insert `b` between
  `l` and `c`, and `b` becomes `c`'s left child.

Either way a run is a **chain**, not a fan of siblings. A chain is ordered
against a concurrent run exactly once, at its head, so the two come out one
after the other. RGA has no left side, so it cannot express the second case and
the backward run fans out.

The origins are found in the **full tree order, tombstones included**. Using the
visible order instead produces a left origin whose right children are all
tombstones: the rule then wants a right origin and there is none. The harness
aborted on that within twenty seeds.

### Sibling order

Children of one node on one side are ordered by `OpId` ascending, where `OpId`
is `(Lamport counter, replica id)` compared lexicographically.

The *direction* is free — it decides only which of two concurrent runs lands
first, and both answers are correct. What is not free is that the order be
**total** and computed from the ids alone. Dropping the replica half leaves
concurrent operations comparing equal, sibling order then depends on the
sequence in which each replica happened to learn of them, and replicas diverge.
That is defect B1 in the report; the harness fails all 240 schedules with it.

## What was rejected

**RGA / Causal Trees / Timestamped Insertion Trees.** Rejected for the backward
interleaving above. Simpler and well understood, and if interleaving were only a
cosmetic risk the simplicity would be worth it. It is not cosmetic: a user who
pastes two paragraphs at one spot on two devices gets them shredded together,
and no later edit repairs it.

**Logoot / LSEQ (dense position identifiers).** Rejected on two counts.
Interleaving is worse than RGA's, not better — concurrent runs at one position
interleave in the ordinary forward-typing case. And identifiers grow without
bound under repeated insertion at one point, so a document's storage depends on
its *edit history* rather than its size. For notes that live for years on a
relay charging for bytes, that is the wrong shape.

**Operational Transformation.** Rejected outright. OT for arbitrary
peer-to-peer topologies needs either a central server to impose an order — which
the threat model forbids, since the relay cannot be trusted to order anything —
or a transformation function whose correctness conditions are famously hard to
satisfy. Umbra has no trusted orderer by construction.

**Yjs's YATA.** Not rejected on the merits; it is a reasonable choice with a
real implementation record. Fugue was preferred because its non-interleaving
property is the one being designed for and is stated as a proof obligation
rather than as observed behaviour, and because the insert rule is two lines that
can be read and checked against the harness.

## Identifiers and clocks

**A Lamport counter plus a replica id. Not a vector clock.**

A CRDT wants two different things from a timestamp:

1. **A total order**, to break ties between concurrent insertions at one
   position. `(counter, replica)` gives it, computed from the id alone so every
   replica agrees without communicating.

2. **Causal readiness** — knowing an operation's prerequisites have arrived. A
   vector clock answers this in general, at one entry per replica that has ever
   existed. Umbra does not need the general answer: every operation names its
   own structural dependency (an insert names its parent node; a delete names
   the nodes it removes), so readiness is "do I hold these specific nodes",
   which is exact and costs nothing per replica.

Vector clocks were rejected on the second point. Device keys rotate
(threat model §4), so the set of replica ids a vault has seen only grows; a
vector clock would carry a slot for every device the user has ever owned, on
every operation, forever.

**Operations are per-run**, not per character. An insert carries a run of text
occupying consecutive counters, and the run's internal shape is implied: each
character after the first is the right child of the one before it, which is what
the insert rule produces anyway. A delete names a run of consecutive ids.

**Every operation has its own identity, including deletes.** A delete takes a
clock tick of its own rather than borrowing the id of what it removes. This is
not tidiness: the oplog is keyed by `(object, replica, counter)`, so a delete
keyed by its target's id lands on the key the insert that created that character
wrote and silently replaces it. Found by `OpLog.AppendsAndReplaysADocument`.

## Encoding, so that encryption changes no CRDT logic

An operation is turned into an opaque byte string by `EncodeOp`, and that string
is the only form anything outside the CRDT ever handles. The oplog stores one;
the relay will forward one. When encryption lands it wraps the payload at that
boundary — AEAD in, AEAD out — and nothing in `src/crdt/text_doc.cc` changes,
because none of it has ever seen a payload.

What is deliberately **outside** the payload is everything the sync protocol
needs in the clear: the object, the replica and the counter, which are the oplog
key. If the counter lived only inside the encoded operation, a relay could not
answer "what have I not seen" without decrypting, and the design would have to
be reopened at exactly the point where reopening is most expensive.

The encoding is canonical and version-tagged. Canonical because two replicas
that encoded one operation differently would store different bytes under one
key, and a future integrity check over the log would report a divergence that
does not exist.

## Tombstone compaction, and the condition under which it is safe

A deleted character cannot simply be removed: it may still hold a position in
the tree that other characters were inserted relative to. So a delete leaves a
tombstone, and an oplog that only grows is not a design that ships.

**The safety condition, stated as the harness forced it to be stated:**

> A tombstone may be dropped when
>
> 1. it is **deleted**, and
> 2. it is a **leaf** — it has no children on either side, because a tombstone
>    with children is still holding their position, and
> 3. every replica has **received** every operation at or below the compaction
>    watermark, and
> 4. every replica **participates in the same compaction round**, and
> 5. a replica that has compacted through a watermark **treats every operation
>    at or below it, and every delete whose TARGET is at or below it, as already
>    seen**.

Conditions 4 and 5 are the ones that are easy to get wrong, and the harness got
them wrong first and then proved they were needed:

- **Condition 4.** The first implementation compacted on one replica at a time,
  at the watermark everyone had provably received. That fails within thirty
  seeds. Having *seen* a node is not the same as being *finished* with it: a
  replica that still holds a tombstone can anchor a new insert to it at any
  moment, because insert origins come from the full tree order. That operation
  names a parent the compacting replica has already dropped, and the two
  documents part company permanently. Compaction therefore needs agreement, and
  the sync protocol owes it.

- **Condition 5, first half.** Dropping a node does not drop the *operation*
  that created it. The oplog still holds it and a peer may hand it back. Re-applying it
  resurrects a character the vault agreed to forget; refusing it as not-ready
  wedges the replica forever, which is what the harness reported as
  "still holds 21 operations it could never apply". So a document remembers how
  far it has compacted and treats anything at or below that as a duplicate —
  sound precisely because condition 3 says everyone already had it.

- **Condition 5, second half — the delete's target, not its id.** A delete takes
  a clock tick of its own, so its id can sit far above the watermark while its
  target sits below it. Two replicas delete one character concurrently; one
  delete becomes everyone's and the character is compacted; the other arrives
  later from a replica whose clock had run ahead, naming a node that no longer
  exists anywhere. Checking the operation's own id does not catch it. This was
  found only when the sweep was widened from 30 seeds to 150 — it appears in 7
  of 1200 schedules, all in `compact-then-edit`, which is the argument for the
  wide lane existing at all.

Chains of tombstones collapse from the outside in: dropping a leaf can make its
parent a leaf, so one pass repeats until nothing moves.

**The round requires that nothing is in flight**, and that is part of condition
4 rather than an implementation detail. An insert issued just before the round,
anchored to a tombstone the round then drops, arrives at a replica that no
longer has its parent — and unlike the delete case there is no sound way to
absorb it, because the characters have nowhere to go. Compaction must therefore
happen at a point where every replica has quiesced, not merely where every
replica has *received* everything.

**The consequence, stated plainly: a device that never participates blocks
compaction for the whole vault.** That is not a flaw in the condition, it is the
condition. The mitigation already exists in the threat model — removing a device
removes it from the acknowledgement set — and the single-user assumption is what
makes the condition checkable at all: the set of replicas is known and
enumerable, which an open collaborative system cannot say.

## What this costs

One node per character, each holding two 24-byte `OpId`s inline: roughly 56
bytes per character, so a 100 KB note is about 5 MB resident while open.
Rendering and index lookup are both a traversal, so both are O(document).

Three optimizations are deliberately not done, and one of them is a trap worth
naming:

- **Run nodes** — storing a run as one node and splitting it only when something
  is inserted into its middle.
- **An order-statistic index**, to make position lookup O(log n).
- **Interned replica ids.** The trap: an interned index must sort the same way
  the `ReplicaId` it stands for does, or sibling order becomes dependent on the
  order in which a replica happened to discover its peers, and replicas diverge.
  It would look like a pure memory optimization.

All three are optimizations of a design whose correctness is the point of this
phase.

## How this is held to account

`sim/` runs seeded schedules over N replicas with partitions, reordering,
duplicate delivery and crash-restart, and checks after each one that all
replicas agree **and** that the agreed document satisfies a reference model
built independently of the CRDT. Convergence alone would be satisfied by every
replica losing the same character.

Seven deliberate defects were introduced one at a time to confirm the harness
goes red; all seven were caught. The table is in the phase report.
